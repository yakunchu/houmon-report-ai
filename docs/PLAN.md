## 0. 結論（1画面まとめ）

- **形**: Next.js（App Router / TypeScript）の1本のWebアプリ。スマホとPCの両方でブラウザから使う。DBなし。
- **個人情報の境界**: 氏名・住所・生年月日などの置き換え（マスク）と、確定後の復元は**すべてブラウザ内**で行う。サーバー（自分の API ルート）と Claude API には**マスク済みテキストだけ**を送る。元の名前と対応表は端末の localStorage に置き、外に出さない。
- **Claude API**: `claude-opus-5-5` を既定にし、**Structured Outputs**（`output_config.format` に JSON Schema）で報告書の全欄を一度に下書きする。選択式の欄は enum に **「要確認」** を含めて「推測で埋めない」をスキーマで強制する。各グループに「根拠（会話からの引用）」を付け、画面で引用の実在をチェックする。
- **Claude Code の機能**: Skills（報告書ルールの正本）、サブエージェント（個人情報監査・評価の読み解き）、フック（APIキー・実データ・`.env` のコミット防止）を使う。MCP は目的に合うものが現時点でないため**使わない判断を説明する**。
- **合格ライン**: 架空患者「山本花子さん」の台本から、見本と同じ選択・備考・SOAP が出ること。これを `npm run eval` で機械的に確認できるようにする。
- **音声入力**: 第1段階はテキスト貼り付け（OSのキーボード音声入力でも可）。第2段階（時間があれば）は**端末内処理（`processLocally`）の Web Speech API のみ**。サーバー送信型の音声認識は個人情報が生の音声で外部に出るため使わない。**11/4 決定: 第2段階は採用せず**（iOS 27 の Safari が `processLocally` 非対応。§4-5）。取り込みはボイスメモの文字起こし → 貼り付け、またはキーボード音声入力（日本語は端末上処理）。

## 2. 全体アーキテクチャ

```
[スマホ / PC のブラウザ]                         [Next.js サーバー (API ルート)]        [Claude API]
 1. 会話テキスト入力（貼り付け / OS音声入力）
 2. 訪問先メモ（氏名・住所・生年月日…）を登録 ── localStorage（端末内のみ）
 3. マスク処理（辞書置換 + 正規表現）─ 端末内
 4. マスク結果の確認画面（置換箇所をハイライト）
 5. 「下書きを作る」 ── マスク済みテキスト + 宛先 ──▶ POST /api/draft
                                                       ・ANTHROPIC_API_KEY は .env（サーバーのみ）
                                                       ・本文はログに残さない、保存しない
                                                       ・system = 報告書ルール（キャッシュ対象）
                                                       ・output_config.format = 報告書スキーマ ──▶ messages.parse
                                              ◀── 報告書 JSON（選択・備考・根拠・SOAP）◀──
 6. 報告書フォーム表示（報告書ソフトと同じ並び）
    ・要確認 バッジ / 根拠引用 / 引用が原文に無ければ警告
 7. 薬剤師が確認・修正 → 確定
 8. 端末内で名前を復元 → 印刷用レイアウト / コピー用テキスト
```

- **個人情報が出る境界は 5 の POST のみ**。送るのはマスク済みテキストと宛先だけ。
- サーバーは状態を持たない（DB なし）。下書きの一時保存は端末の localStorage。
- Claude API 側の保持は 30 日以内削除・学習不使用（§1）。それでもマスクするのは「二重の守り」。実運用時の医療情報の取扱い基準の確認は本計画の範囲外（ハッカソン提出後の課題として README に明記）。

## 3. 画面と機能

### MVP（11/4 までに動かす）
1. **入力画面**: 大きなテキスト欄。宛先（医療機関／ケアマネ／その他）の切替。
2. **訪問先メモ**: 患者名・家族名・住所・生年月日・電話など、端末に保存。1人分で可（複数患者は拡張）。
3. **マスク確認画面**: 置換箇所を色付きで表示。辞書に無いが名前らしい語（「○○さん」「○○様」の直前など）は**黄色で警告**し、タップで辞書に追加できる。ここを通らないと送信できない。
4. **下書き生成**: 進行表示付き。失敗時（refusal / max_tokens / タイムアウト / 429）は分かる言葉で表示し再試行できる。
5. **報告書フォーム**: `CLAUDE.md` の表の並び。各欄 = 選択肢（ラジオ／セレクト）+ 備考（自由入力）。会話に根拠が無い欄は空欄のまま「要確認」バッジ。各グループに「根拠」（会話からの引用）を折りたたみ表示。SOAP の S は引用そのまま。
6. **確定 → 出力**: 名前を復元した「完成テキスト」。コピー・印刷（A4 想定、`@media print`）。宛先で文頭の宛名だけ変わる。

### 拡張（11/5 以降、時間があれば）
- 複数患者の訪問先メモ、下書き履歴（端末内）。
- 端末内音声認識（§4-5）。
- 2 つ目の架空台本（ケアマネ宛）での評価。
- スマホのホーム画面追加（PWA 最小構成）。

### 患者リスト（11/4 追加。社長の要望）
- 背景: 基本情報を毎回入力するのは負担。患者リストから選ぶだけにする。
- データ: 患者 1 件 = 基本情報一式（氏名・カナ・生年月日・住所・家族（実名はマスク用）・宛名・訪問頻度・調剤形態・服薬管理者・管理方法・処方・定型欄・所属グループ）。**端末内の localStorage のみ**（`src/lib/patients/`）。サーバーにも API にも送らない。訪問ごとに変わる項目（宛先種別・報告日・次回訪問日）と下書きは患者マスターに持たない。
- 検索: 氏名・カナ（ひらがな・半角カナの違いを吸収）・生年月日（西暦の各表記と和暦）。
- グループ: 施設や訪問曜日などを登録。1 人が複数グループに入れる。グループ内はあいうえお順（カナ、`Intl.Collator("ja")`）か手動（↑↓）に切替。
- 新しい患者の流れ: 「＋ 新しい患者」→ 氏名・カナ・生年月日（マスクに必要な最小限）→ 会話を取り込んで下書き → AI が会話から読み取れた基本情報（`basicInfoSuggestions`: 訪問頻度・調剤形態・家族の関与、および服薬管理者・管理方法）を**空欄にだけ自動入力**し「AI の提案」と表示 → 薬剤師が確認して「患者リストに保存」。既に値がある項目は「記録 → 会話」の差分を見せて手動反映。
- 既存の保存済み基本情報は初回起動時に患者 1 件として自動移行。架空サンプル（山本花子さん）はリストに「（架空）」付きで入る。
- **書き出し・読み込み（11/4 追加）**: 端末ごとに別のリストになるため、JSON ファイルで移す。書き出しは利用者が押したときだけ（実名を含む旨を確認）、iPhone では「ファイル」アプリに保存 → AirDrop などで PC へ。読み込みは「追加・更新」（氏名＋生年月日が同じ人は同じ患者として `updatedAt` が新しい方を採用。グループは名前で突き合わせ、id は端末側を維持）と「置き換え」（確認あり）。適用前に内訳（追加・更新・変更なし・グループ追加）を表示。サーバーは介さない。暗号化は Web Crypto が secure context 限定のため、11/6 の HTTPS 対応後の候補（パスフレーズ付き書き出し）。

### 画面方針
- 文字は大きく（本文 18px 以上、選択肢ボタンは指で押せる高さ）。色だけで意味を伝えない（「要確認」は文字でも表示）。
- 画面案が必要なら Claude Design で 1〜2 案作ってから実装（任意。グローバルルールに従い、実装コード自体は Claude Code で書く）。

## 4. Claude API の使い方

### 4-1. モデルと設定
- 既定 `claude-opus-5-5`（claude-api スキルの既定）。`effort` は明示する（まず `medium`、評価で `high` と比較）。
- `MODEL` を環境変数で切替可能にし、`claude-sonnet-5-5` を同じ評価で比較（速さ重視の訪問先利用を想定）。採用は評価結果と体感速度で決める。
- **11/4 の比較結果（ルール改訂 3 のプロンプト、各条件 1 回。`eval-results/history.md`）**:

  | モデル / effort | 山本さん台本 | 聞き返し台本 | 所要（山本／聞き返し） | 出力トークン |
  |---|---|---|---|---|
  | Opus 5.5 / medium（旧既定） | 13/13、S は 2 件 | 13/13、内容理解要確認 ○ | 19.4 秒／19.7 秒 | 2,206 |
  | **Opus 5.5 / low（新既定）** | 13/13、S が見本と完全一致 | 13/13、要確認 ○、O に聞き返しの事実も記載 | 9.6 秒／10.7 秒 | 1,240 |
  | Sonnet 5.5 / medium | 13/13、S 類似 0.80 | 13/13、要確認 ○（聞き返しの事実は O に書かず） | 7.3 秒／8.3 秒 | 1,211 |

  → 既定を **Opus 5.5 / effort low** に変更（精度を落とさず所要が半分）。Sonnet 5.5 は `HOUMON_MODEL` で選べる高速な代替。各条件 1 回の測定なので、台本が増えたら再確認する。
- 非ストリーミングの `client.messages.parse()` + `zodOutputFormat()`（`@anthropic-ai/sdk/helpers/zod`）。`max_tokens` は 16000（上限であり消費量ではない）。
- `stop_reason` を必ず確認: `refusal`（200 で返る）→「下書きを作れませんでした」表示、`max_tokens` → 上限を上げて再試行。

### 4-2. 報告書スキーマの設計（Structured Outputs の制限に合わせる）
制限（任意パラメータ 24、union 16）を**使い切らない**設計にする:
- **全プロパティを `required`** にする（任意 0、union 0）。
- 選択式の欄は `enum` に本来の選択肢 + **`"要確認"`** を持たせる。`null` や `["string","null"]` は使わない。
- 備考は `string`（根拠が無ければ空文字 `""`）。
- 数値欄（食事回数）も `string`（例 `"3"`、不明なら `"要確認"`）にして union を避ける。数値制約はスキーマで表せないため、画面側で検証。
- 「○日毎」「○時間○分」のような補足値は備考に書く運用にし、スキーマは単純に保つ。

| グループ | 欄 | 型 |
|---|---|---|
| 宛先 | 宛先 | enum: 医療機関／ケアマネ／その他／要確認 |
| 訪問 | 訪問頻度 | enum: 1週間毎／2週間毎／1か月毎／その他／要確認 + 備考 |
| 服薬 | 調剤形態、服薬管理者、管理方法、服薬状況 | 各 enum + 備考 |
| 残薬 | 残薬 | array of {薬剤名: string, 残数: string, 備考: string}（0件可） |
| 食事 | 量、回数、嚥下 | enum / string / enum + 備考 |
| 排泄 | 尿頻度、便通 | enum + 備考 |
| 睡眠 | 日中、夜間 | enum + 備考 |
| 運動・移動 | 運動、移動 | enum + 備考 |
| 傾向 | 日常でみられる傾向 | enum: 特になし／有／要確認 + 備考 |
| 指導内容 | S・O・A・P | 各 string（S は本人の言葉の引用） |
| 定型 | 指導相手、後発品希望、お薬手帳 | 選択肢は見本を見て決める（§11） |
| 根拠 | グループごとの `根拠` | string（会話からの引用、無ければ `""`） |

- **根拠はグループ単位**（欄ごとにすると項目数が約3倍になり、コンパイル上限に当たる恐れ）。初日にこのスキーマがコンパイルできることを確認する（「Schema is too complex」が出たら根拠をさらに集約）。
- enum 値の大文字小文字は保証されないため、比較は正規化して行う（今回の選択肢は日本語なので実害は小さい）。
- スキーマの `enum` や説明文に個人情報を入れない（公式の注意事項）。架空データでも患者名はスキーマに書かない。

### 4-3. システムプロンプト（= Skill の正本）
- `prompts/report-rules.md` を正本とし、アプリは**ビルド時に TS 定数へ生成**して読み込む。Claude Code の Skill も同じファイルを参照する（§5-1）。
- 内容: 役割（書類の下書き支援であり医療判断はしない）、各欄の選択基準、「会話に根拠が無い欄は要確認、推測で埋めない」、S は原文引用、備考の書き方、根拠の書き方、口語→報告書の文体変換の例。
- 512 トークン以上になる見込みなので `cache_control` を付ける（開発中の繰り返し実行と、同じ日に複数件作る場面で効く）。effort を変えるとキャッシュが切れるため、比較実験は時間を分けて行う。

### 4-4. 引用照合（AIは下書き、判断は薬剤師）
- 返ってきた `根拠` と `S` が、送ったマスク済みテキストに実在するかを**画面側で照合**（空白・句読点を無視した部分一致）。見つからなければ「原文にない引用」警告を付け、薬剤師の確認を促す。
- 「要確認」の欄は未選択のまま表示し、確定時に未選択が残っていれば一覧で知らせる（空欄のまま確定することも可能）。

### 4-5. 音声入力（第2段階・任意）
- 第1段階: テキスト貼り付け。スマホではキーボードの音声入力でそのまま欄に入力できる（処理場所は OS 依存で、本計画では未確認）。
- 第2段階: `SpeechRecognition.available({langs:["ja-JP"], processLocally:true})` が `available`（または `downloadable` → `install()` 成功）のときだけ録音ボタンを有効化。`processLocally = true` 固定。`unavailable` の端末には「この端末では端末内音声認識が使えません」と表示して第1段階に誘導。
- **使わないもの**: サーバー送信型の Web Speech（既定動作）、外部の文字起こし API（生の音声に実名が含まれる）。ブラウザ内 Whisper は期間内の実装・検証が重く見送る。
- 日本語の端末内認識が社長の端末で使えるかは**未確認** → 11/3 に実機（スマホ・PC）で `available()` の値を確認し、第2段階の可否を決める。
- **決定（11/4、社長）: 方針 A**。実機診断（§4-6 の `/diag` 結果）で iOS 27 の Safari は `processLocally` 非対応・`available()` 未実装と分かったため、第2段階（アプリ内の音声認識）は**採用しない**。アプリ内録音も作らない（文字起こしが得られず「聞き直し」以上の価値が薄い。端末内に会話音声が残る管理も増える）。代わりに取り込み導線を整える: ②会話に「会話の入れ方」（ボイスメモの「文字起こしを表示」→ コピー → **「クリップボードから貼り付け」ボタン**／キーボード音声入力は日本語が端末上処理）を置く。ブラウザ内 Whisper（完全端末内）は未検証・重いため締切後の将来案。
- **11/5 実機確認（社長）**: iPhone（https）で ②会話 → マスク → 下書き → ④出力まで通しで動作。キーボード音声入力が英語になったのは英語キーボードのまま使ったためで、地球儀キーで日本語に切り替えれば日本語になる（Apple のガイド: 音声入力はキーボードの言語に従う）。
- マイク利用は HTTPS（または localhost）が必要。スマホ実機で音声を試すには HTTPS の配信先が要る（§4-6）。

### 4-6. 開発中にスマホから HTTPS で開く方法（方針案・2026-11-02 追記、実装は 11/6）

**背景**: `getUserMedia`（録音）と `navigator.clipboard` は secure context（https か localhost）でしか使えない。Chromium の定義では secure origin は https／wss／localhost／127.0.0.0/8／::1 などで、LAN の `http://192.168.x.x:3000` は含まれない（出典: Chromium「Prefer Secure Origins For Powerful New Features」）。文字入力の経路は http のまま動く（`next.config.ts` の `allowedDevOrigins` に `192.168.x.x` と `192.168.x.*` を登録済み。Next.js は `localhost` 以外のオリジンからの `/_next/*` をブロックするため。`*` はホスト名の 1 ラベル＝IP では 1 オクテット）。コピーは http でも動くよう `textarea` + `document.execCommand("copy")` の予備手段を入れた。

| 方法 | 手順の概要 | 長所 | 短所・リスク | 向く場面 |
|---|---|---|---|---|
| **A. 自前証明書 + `next dev --experimental-https`** | mkcert で LAN IP を含む証明書を作る（例: `mkcert 192.168.x.x localhost 127.0.0.1 ::1`）→ `next dev --experimental-https --experimental-https-key <key> --experimental-https-cert <cert>` → スマホに `rootCA.pem`（`mkcert -CAROOT` の場所）を入れて信頼する。iOS: AirDrop かメールで開く → 設定「プロファイルがダウンロードされました」でインストール → 設定 > 一般 > 情報 > 証明書信頼設定 で「ルート証明書を全面的に信頼」を ON（出典: mkcert README、Apple サポート 102390）。Android: ユーザー証明書として CA をインストール | LAN 内で完結し第三者を経由しない。iPhone・Android 両方で使える。一度入れれば以後は安定 | 初回設定に手間。PC の IP が変わると証明書の作り直し（ルーターの DHCP 固定割当で回避）。**Next 同梱の自動生成証明書は `localhost` / `127.0.0.1` / `::1` だけ**で LAN IP を含まない（確認済: `node_modules/next/dist/lib/mkcert.js`）ので、自前の証明書が必須。開発用 CA をスマホに入れる（`rootCA-key.pem` は PC 外に出さない） | **本命**（11/6 の録音開発） |
| **B. Android Chrome のフラグ** `chrome://flags/#unsafely-treat-insecure-origin-as-secure` に `http://192.168.x.x:3000` を登録 | スマホの Chrome で設定、2〜3 分 | 証明書不要で最速 | Android Chrome だけ（iPhone の Safari には無い）。Chromium の資料は「そのセッション・そのオリジンだけ secure 扱い」とし、Android での可否は chrome://flags 形式については明記なし（コマンドライン版は root が必要と記載）→ 実機で要確認（出典: Chromium「Deprecating Powerful Features on Insecure Origins」） | 社長のスマホが Android なら、録音 UI の即日確認用 |
| **C. Cloudflare Quick Tunnel** `cloudflared tunnel --url http://localhost:3000` | `cloudflared` を PC に入れて起動 → 表示される `trycloudflare.com` の URL をスマホで開く | Cloudflare アカウント不要。証明書不要。LAN の外からも開ける | **URL を知っていれば誰でも開発サーバーに到達できる**（API キーはサーバー側にあるので第三者に使われる恐れ）→ `--allowed-mail` のメール認証ゲートを必ず併用。通信は Cloudflare を経由（マスク済みの会話が通る）。URL は起動ごとに変わり、稼働保証なし、同時 200 リクエストまで、開発・テスト用途と明記。`allowedDevOrigins` に `*.trycloudflare.com` の追加が必要（出典: Cloudflare「Quick Tunnels」） | 自宅 LAN の外でのデモ、CA を入れられない端末 |
| **D. 早期デプロイ（Vercel 等）** | GitHub 連携でデプロイし、環境変数にキーを置く | 本番に近い確認。HTTPS は自動 | 公開 URL + サーバー側 API キー → 認証を付けないと誰でも API を使えてしまう。11/7 の「安全に公開する方法」を聞いてから判断（社長の方針） | 提出直前 |

**方針（2026-11-02 確定。社長のスマホは iPhone）**: **A で進める。B（Android Chrome のフラグ）は対象外。** C は LAN 外でのデモの予備（必ず `--allowed-mail` 付き）。D は 11/7 以降。いずれも `allowedDevOrigins` はホスト名で判定されるため https でも必要。

**11/4 実施**: mkcert ではなく **OpenSSL（Git for Windows 付属）** で開発用 CA と LAN IP 入りのサーバー証明書を作る `scripts/make-dev-cert.mjs`（`npm run cert:dev`）、`npm run dev:https`、CA を LAN 内の iPhone に配る `scripts/serve-ca.mjs`（`npm run serve:ca`。公開鍵の `rootCA.pem` だけを `application/x-x509-ca-cert` で配り、QR と手順ページを出す）を用意。Next.js は鍵と証明書を渡すと mkcert を取りに行かないことを `next/dist/cli/next-dev.js` で確認。証明書は Apple の要件（RSA 2048・SHA-256・SAN・EKU serverAuth・398 日以内）に合わせた。残りは iPhone 側の CA 導入（社長）と、警告なしで開けることの確認。**11/4 夜**: iPhone で `https://192.168.x.x:3000` が開けた。「鍵マークが出れば完了」と案内したのは誤りで、iOS 26・27 の Safari はアドレスバーに鍵マークを出さない。Apple の iPhone ユーザガイド（iOS 26 版・iOS 27 版とも）は暗号化の確認を「検索フィールド左のページメニュー → 接続セキュリティの詳細」で行う手順にしており、鍵マークには触れていない。信頼されていない証明書なら Safari は警告を出し、HTTPS でない・証明書がない場合は検索フィールドに「安全ではありません」と出る（同ガイド「デジタル証明書と暗号化されたWebサイト」）。

11/6 の手順（iPhone 向け）:
1. PC で mkcert を用意する（Next が `--experimental-https` の初回に取得する mkcert バイナリの流用か、winget 等での導入。当日に一次情報で確認）。`mkcert -install` のあと `mkcert 192.168.x.x localhost 127.0.0.1 ::1` で LAN IP 入りの証明書を作る（PC の IP は DHCP で変わり得るので、ルーターで固定割当にするか、変わったら作り直す）。
2. `package.json` に `dev:https`（`next dev --experimental-https --experimental-https-key <key> --experimental-https-cert <cert>`）を足す。証明書と鍵は git 管理外に置く（`.gitignore` に追加。`rootCA-key.pem` は PC の外に出さない）。
3. iPhone に `rootCA.pem`（`mkcert -CAROOT` の場所）を AirDrop かメールで送って開く → 設定「プロファイルがダウンロードされました」からインストール → 設定 > 一般 > 情報 > 証明書信頼設定 で「ルート証明書を全面的に信頼」を ON（出典: mkcert README、Apple サポート 102390）。
4. Safari で `https://192.168.x.x:3000` を開き、「この接続はプライベートではありません」の警告なしで開けること（＝CA が信頼されている）、ページメニュー → 「接続セキュリティの詳細」で発行者が houmon-report-ai dev CA と出ること、`window.isSecureContext` が true になること、マイク許可のダイアログが出ることを確認する。鍵マークは確認基準にしない（iOS 26・27 の Safari には出ない）。
5. 録音の設計判断（§4-5）: Safari の `webkitSpeechRecognition` が端末内処理（`processLocally`）に対応しているかは未確認なので、まず `SpeechRecognition.available({ langs: ["ja-JP"], processLocally: true })` の戻り値を実機で確かめる。`unavailable` なら、録音は MediaRecorder で端末内に音声を残すだけにし、文字起こしは iPhone のキーボード音声入力（第1段階の経路）を使う方針に切り替える。サーバー送信型の音声認識は使わない。
   **11/4 夜 実施**: iPhone で CA を信頼し、`https://192.168.x.x:3000` が警告なしで開けた（HTTPS OK）。この判断を実機で行うために**端末診断ページ `/diag`**（`src/app/diag/page.tsx`、`src/components/diag/DeviceDiag.tsx`、`src/lib/diag/device.ts`）を追加: 開いた URL と `isSecureContext`、`getUserMedia` の有無、`MediaRecorder` の対応形式、`SpeechRecognition` の有無、`processLocally` の指定可否、`available()`（端末内処理あり／なし）の戻り値、userAgent を表にし、ボタンで「マイク許可」「3 秒録音して再生」「端末内音声認識（processLocally を指定できる端末だけ）」を試せる。結果は文章にしてコピーできる。患者データは扱わない。noindex。
   **11/4 19:40 実機結果（社長の iPhone、iOS 27.0.1 / Safari 27.0.1）**: https で isSecureContext=はい、getUserMedia あり、MediaRecorder あり（audio/mp4 ほか）、マイク許可 OK（48000 Hz）、3 秒録音 OK（audio/mp4; codecs=mp4a.40.2、68 KB、再生可）。音声認識は `webkitSpeechRecognition` のみで、**`processLocally` は指定できず `available()` も未実装** → Safari では端末内処理を保証した音声認識が使えないため、**アプリ内の音声認識は採用しない**（方針どおりサーバー送信型は使わない）。録音（端末内保存）は技術的に可能。
   **代わりの文字起こし経路（Apple の一次情報で確認、11/4）**: ① iPhone のキーボード音声入力は「多くの言語の音声入力は iPhone 上で処理されます。インターネット接続は必要ありません」（iPhone ユーザガイド iOS 27「テキストを音声入力する」）。Apple の「iOS と iPadOS 27 で利用できる機能」の「音声入力：デバイス上でのモードレスな音声入力」の一覧に**日本語**が入っている。無音 30 秒で自動停止。② ボイスメモの文字起こしは「対応しているモデルの…日本語…で利用できます」（iPad ユーザガイド iPadOS 27「ボイスメモの文字起こしを表示する」。録音中・録音後に表示、テキストをコピー可）。**処理がデバイス上かどうかは Apple の資料で確認できていない**。③ 同ページの一覧では「メモ：オーディオの文字起こし」も日本語に対応。
6. 証明書の有効期限や IP 変更で開けなくなったときの復旧手順を README に書く。

## 10. コスト見積り（確認済み料金ベース）

### 見本から分かった設計上の補足
- 報告書は「基本情報（宛先・患者・薬局・訪問頻度・次回訪問日・調剤形態・服薬管理者・管理方法）」「処方内容」「会話から埋める欄」「SOAP」「定型欄」の 5 ブロック。**AI が埋めるのは「会話から埋める欄」と SOAP、および服薬管理者・管理方法の備考**。基本情報と処方内容は薬局側の既存データ（端末内で手入力・保存）で、AI には**文脈として**渡す（例: 一包化・就寝前のセンノシドが処方にあると分かるので、残薬の記述や A/P に使える）。
- 見本の O の書き出し「処方内容の薬効・用法を説明、内容理解OK」、P の「残薬は次回処方で日数調整を医師に提案」「ケアマネジャー様への依頼」は、この薬局の報告書の**書き方の型**としてルール（Skill）に一般化して載せる。見本の文そのものはプロンプトに入れない（評価が意味を失うため）。
- 台本は熊本の方言を含む。方言のまま正しく読み取れることを評価で確認する。

## 12. 社長の決定（2026-11-05 夜）と、ハッカソン後の課題

出力形式の調査メモ（`docs/RESEARCH-report-formats.md`）を読んだ社長の決定。締切まで 3 日のため、やることとやらないことを分けた。

### 今回やる（11/6 まで）

### 今回やらない（ハッカソン後の課題）
- パスワード付き PDF（方式とパスワードの渡し方を先に決める）
- 宛先の選択肢に「介護職」を新設すること（報告書ソフトの並びと食い違うため見送り）
- 欄の追加: 訪問目的・主訴・薬物有害事象（なし／あり）・次回への申し送り（スキーマと評価の見本の変更が要る）

- トレーシングレポートの同時下書き: 在宅の算定月は服薬情報等提供料を算定できないため、構想から外す
- ④出力の「読み手: 介護職」切替（SOAP を載せず、お願い・観察の箇条書き）: 11/6 に見送りを決定。稽古と録画を優先
- 施設をまたぐ検索: 画面 v2 の検索は個人宅の一覧だけ。施設の入居者は一覧から探すしかないので、施設をまたいだ氏名・カナ・生年月日の検索を足す

- Claude Design での画面案の作成: 画面 v2 は締切前日で時間がなく、画面案を作らずアプリのトークンで直接実装した。ハッカソン後に Design で整理し直す

- **録音→文字起こしのショートカット連携（11/6 社長の実機テスト）**: iPhone（iOS 27.0.1）で、ショートカットの「オーディオを録音 → オーディオを文字起こし → クリップボードにコピー」が**機内モードでも動いた**（端末内処理の状況証拠。Apple の明記は無い）。`/transcript-check` でボイスメモ（A）とショートカット（B）の一致率を比べ、読み間違いの範囲で**差なし**（数値は未記録）。→ A 案を採用: ②に「録音して文字起こし」ボタン（11/7 に②の先頭へ移し、花田色の大きなボタンに）（`shortcuts://run-shortcut`）と、URL の `#t=` から会話欄へ自動で入れる受け口を実装。社長の検索で、ボイスメモにも「録音を開始」のショートカット用アクションがあることが分かった（Apple の文書では未確認だった）。長時間録音の安定性は未確認で、止まるならボイスメモで録音する B 案に切り替える。
- **x-callback-url は不採用（11/6 夜、社長の実機テスト）**: ショートカット側の編集を不要にするため、ボタンを x-callback-url（`x-success=<アプリの URL>/#t=`）に変えて試した（c110c1b）。iOS 27.0.1 は文字出力を `#` の後ろではなく**クエリ `?result=`** として付けて戻し、PC の開発サーバーの要求ログに文字起こしの中身が残った（`GET /?result=…`）。「`#` より後ろはサーバーに届かない」前提が崩れるため `shortcuts://run-shortcut` に戻し、ショートカットの最後の「URL を開く」（`#t=`）で渡す形を正とした。`?result=` で届いた場合は取り込まず警告だけ出す。知らせの帯（青・赤）が自動スクロールで画面の上に隠れて見えなかった不具合（社長に警告が見えなかった原因）も直した。配布の課題（iPhone ごとに URL を 1 行直す）は残る。→ **11/7 未明、戻した形を社長の実機で確認**: ②のボタン → 録音 → 停止 → アプリが開いて文字が入り、青い帯が出た。サーバーログは `GET /` のみ（`?result=` なし）。この形で確定。

### 11/7 の決定（社長の UI 相談 → 画面 v2）
- 社長の要望: 患者を選ぶところがごちゃごちゃして分かりにくい。長い 1 ページを下にスクロールする形ではなく**タブが切り替わる画面**にし、**「戻る」「次へ」を常に置く**。**最初の画面は患者選び**で、**個人宅／施設**を選ぶ。個人宅は**五十音順**が基本で、**グループ別・曜日別**に切り替えられる。施設も同じ。**表示順は指でつかんで動かせる**。患者の常時画面に**赤い「申し送り・注意事項」ボタン**。使う人は薬剤師だけでなく介護職・高齢の方も。
